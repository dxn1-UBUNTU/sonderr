# Advanced debugging techniques

Effective debugging goes beyond reading error messages. It requires systematic isolation of variables, hypothesis-driven investigation, and evidence-based conclusions. When a bug manifests, resist the urge to immediately change code. First, reproduce the issue reliably and understand the exact conditions that trigger it.

## Isolation strategies

- Reduce the failing case to the smallest reproducible example. Remove unrelated code paths until the bug persists in the simplest possible setup.
- Use binary search on changes: if a recent change introduced the bug, revert halves of the change set to narrow the fault region.
- Compare working and broken environments side by side. Differences in dependencies, configuration, or input data often reveal the root cause.

## Instrumentation and logging

- Add temporary instrumentation with clear, scoped log statements that include identifiers, timestamps, and state snapshots.
- Use structured logging when available so you can filter and correlate events across services or modules.
- Remove or downgrade debug instrumentation before merging. Production logs should be intentional, not accidental.

## Debugger usage

- Set breakpoints at the entry point of the failing operation, not arbitrarily inside the function body.
- Step through the execution path while inspecting variable state at each transition. Watch for unexpected mutations or type mismatches.
- Use conditional breakpoints when the bug only occurs under specific data conditions. This avoids manual repetition.

## Common pitfalls

- Do not fix symptoms. Addressing the immediate error without understanding why it occurred usually produces a second bug nearby.
- Do not assume the stack trace tells the whole story. Errors can be thrown from helper code that receives bad input from upstream logic.
- Do not debug in isolation for too long. If you are stuck after reasonable investigation, re-examine the surrounding context or ask for a second perspective.

## Test types and when to use them

- Unit tests: validate individual functions or classes in isolation. Use them for business logic, pure functions, and edge cases.
- Integration tests: verify that multiple components work together correctly. Use them for API endpoints, database interactions, and module boundaries.
- End-to-end tests: exercise the full system from user input to final output. Use them for critical user journeys and deployment gates.

## Writing effective tests

- One assertion concept per test when practical. Multiple assertions are fine when they verify a single coherent outcome.
- Name tests descriptively. A test name should read like a sentence: `should return empty list when input is null`.
- Use the Arrange-Act-Assert pattern. Setup the state, execute the operation, then assert the outcome.
- Avoid testing implementation details. Test public behavior and contracts, not internal variable names or call counts.

## Test data and fixtures

- Build test data that mirrors real-world edge cases: empty inputs, large inputs, malformed inputs, and boundary values.
- Use factories or builders for complex objects instead of hand-coding identical setup in every test.
- Keep test data deterministic. Random values and live network calls make tests flaky and hard to debug.

## Coverage and quality

- Aim for meaningful coverage, not arbitrary percentages. A well-tested critical path is more valuable than full coverage of trivial getters.
- Run tests in CI on every pull request. If tests are skipped or ignored, investigate why before merging.
- When a test fails, treat it as a signal to investigate rather than an obstacle to bypass. Flaky tests should be fixed or quarantined, not deleted.

## Verification checklist

- [ ] New features include unit and integration tests.
- [ ] Bug fixes include regression tests that would have caught the original issue.
- [ ] Tests pass locally and in CI.
- [ ] No tests are silently skipped or marked as TODO without a tracking issue.


# Code review practices

Code review is a collaborative quality gate. The goal is to catch defects, share knowledge, and maintain consistency across the codebase. Review both the change and its context.

## What to look for

- Correctness: Does the change do what the author intended? Are edge cases handled?
- Clarity: Is the code readable? Do variable names, function names, and structure communicate intent?
- Consistency: Does the change follow existing patterns in the codebase? Are there deviations that should be standardized?
- Security: Are secrets, user input, or external data handled safely? Is there injection risk or unsafe deserialization?
- Performance: Does the change introduce unnecessary allocations, blocking operations, or repeated work?

## Review etiquette

- Be specific. Instead of "this is confusing," say "this logic is hard to follow because `x` is mutated in two places; consider extracting a helper."
- Separate nitpicks from blockers. Use clear labels or structure so the author knows what must change versus what is optional improvement.
- Ask questions instead of demanding changes when you lack full context. "What happens if the array is empty?" is more useful than "handle the empty case."
- Approve when the change is good enough. Perfectionism slows teams. If the code is correct, clear, and consistent, approve it.

## Responding to review feedback

- Address every comment, even if just to acknowledge it or explain why you disagree.
- Do not take feedback personally. Review is about the code, not the author.
- When feedback reveals a misunderstanding in the original code, fix the code or add a comment rather than arguing semantics.
- Squash follow-up commits when possible. A clean review history is easier to audit than a trail of tiny fix commits.

## Measuring before optimizing

- Profile before changing code. Use language-native profilers, flame graphs, or request-level timing to identify hot paths.
- Establish a baseline. Record metrics before and after every optimization so you can prove the change helped.
- Focus on the critical path. A 10% improvement in code that runs 80% of the time is more valuable than a 50% improvement in rarely-executed code.

## Common optimization patterns

- Reduce allocations in hot loops. Reuse objects or use pool allocation when the allocation rate dominates runtime.
- Batch I/O operations. Combine multiple small reads or writes into fewer, larger operations.
- Cache repeated computation. Memoize pure functions or store frequently accessed derived data.
- Avoid unnecessary copies. Pass references or spans when the data is large and the operation is read-only.
- Parallelize independent work. Use worker pools or async dispatch when tasks do not share mutable state.

## When not to optimize

- Do not optimize prematurely. Readable, maintainable code is more valuable than fast code that no one can understand.
- Do not optimize without data. If profiling shows a function takes 0.1% of runtime, making it 10x faster saves almost nothing.
- Do not sacrifice correctness. An optimized bug is still a bug.

## Input handling

- Treat all external input as untrusted. Validate, sanitize, and enforce strict schemas before using user-provided data.
- Use parameterized queries for database access. Never concatenate user input into SQL, NoQL, or command strings.
- Enforce size limits on inputs. Unbounded strings, arrays, or JSON payloads can exhaust memory or trigger denial of service.

## Secrets and credentials

- Never log secrets, API keys, tokens, or passwords. Redact sensitive fields in all log output.
- Store credentials in environment variables or dedicated secret managers. Do not hardcode secrets in source files or configuration templates.
- Rotate secrets regularly. If a secret is exposed, revoke it immediately and audit access logs.

## Dependency security

- Audit dependencies before adding new ones. A small, well-maintained library is usually safer than a large, rarely-updated one.
- Keep dependencies up to date. Use automated tools to detect known vulnerabilities and patch them promptly.
- Pin dependency versions in production. Floating versions can introduce unexpected breaking changes or malicious updates.

## Secure defaults

- Fail closed. When a permission or feature flag is ambiguous, deny access rather than grant it.
- Use HTTPS for all external communication. Do not transmit sensitive data over unencrypted channels.
- Implement least-privilege access. Services and users should have only the permissions they absolutely require.

## Principles

- Write for the reader, not for yourself. Assume the reader has context about the domain but not about your specific implementation.
- Keep documentation close to the code. Inline comments explain why, README files explain how to run and build, and architecture docs explain design decisions.
- Update documentation when code changes. Stale documentation is worse than no documentation because it misleads readers.

## README standards

- Include a one-paragraph project description.
- List prerequisites and setup steps in the order a new contributor would need them.
- Provide commands for building, testing, linting, and running the project.
- Document configuration options, environment variables, and external dependencies.

## Inline comments

- Explain why something is done, not what is done. The code already shows what is done.
- Document non-obvious decisions, workarounds, and tradeoffs. Future maintainers need to understand the constraints that shaped the code.
- Avoid comments that restate the code. "Increment counter" above `counter++` is noise.

## API and interface documentation

- Document public APIs with clear descriptions, parameter types, return types, and error conditions.
- Include usage examples for complex APIs. A short code example is worth paragraphs of prose.
- Keep changelogs. Record breaking changes, migration steps, and deprecation timelines.

## Error classification

- Operational errors: expected failures such as network timeouts, invalid user input, or missing files. These should be handled gracefully.
- Programmer errors: bugs such as null dereferences, type mismatches, or invalid state. These should fail fast and loudly.
- External failures: issues caused by downstream services, third-party APIs, or hardware. These require retry logic and fallback behavior.

## Design principles

- Fail fast for programmer errors. Do not silently swallow bugs. Let them propagate to a handler that can decide whether to retry, fallback, or abort.
- Provide context. Errors should include enough information to diagnose the problem without additional investigation. Include identifiers, operation names, and relevant state.
- Do not expose internals to users. Translate low-level errors into user-friendly messages without leaking stack traces or system paths.

## Retry and timeout patterns

- Use bounded retries with exponential backoff for transient failures. Infinite retries amplify outages.
- Set explicit timeouts on all I/O operations. Unbounded waits hang threads and exhaust connection pools.
- Distinguish between retryable and non-retryable errors. Validation errors and authentication failures should not be retried.

## Error boundaries

- Define error boundaries at service and module interfaces. Catch errors at the boundary, transform them into domain-specific errors, and propagate them upward.
- Avoid catching broad exception types unless you are at a top-level boundary. Catching `Exception` or `Throwable` everywhere hides bugs.
- Log errors at the boundary with full context, then return a sanitized result to the caller.

## When to refactor

- Before adding a feature if the current structure makes the change risky or unclear.
- After fixing a bug if the fix reveals fragile or duplicated logic.
- When onboarding new contributors if the code is hard to understand.
- When the team has explicit capacity and a clear scope. Refactoring without a goal creates endless churn.

## Safe refactoring practices

- Keep tests green throughout. If tests are missing, write characterization tests that capture current behavior before refactoring.
- Make small, reversible changes. Extract a function, rename a variable, or inline a helper. Do not rewrite large modules in one step.
- Use version control branches. This makes it easy to abandon a refactor that is not working out.
- Refactor one concern at a time. Do not mix behavior changes with structural changes in the same diff.

## Common refactoring patterns

- Extract function: pull a complex block into a well-named function to clarify intent and enable reuse.
- Rename for clarity: replace abbreviations and ambiguous names with descriptive ones.
- Remove duplication: consolidate repeated logic into shared utilities, but only when the duplication is truly the same concept.
- Simplify conditionals: replace nested if-else chains with early returns, guard clauses, or polymorphism.
- Reduce coupling: separate concerns by moving logic closer to the data it operates on.

## Avoiding over-engineering

- Do not introduce abstractions for hypothetical future requirements. Build for the current need and refactor when the need actually expands.
- Do not create frameworks within the project. Standard libraries and established patterns are usually sufficient.
- Prefer composition over inheritance. Deep inheritance hierarchies are hard to reason about and fragile under change.

## Deployment principles

- Deploy small, frequent changes. Small diffs are easier to review, easier to rollback, and easier to debug when something goes wrong.
- Automate deployments. Manual steps introduce human error and create bottlenecks.
- Use immutable infrastructure. Treat deployed artifacts as disposable; reconfigure by replacing, not patching.
- Separate deployment from release. Deploying code to production does not mean all users see the new behavior immediately.

## Pre-deployment checks

- Run the full test suite in an environment that matches production as closely as possible.
- Verify that configuration, secrets, and environment variables are present and correct in the target environment.
- Check that database migrations are idempotent and reversible.
- Confirm that monitoring, alerting, and log aggregation are active and correctly configured.

## Rollback strategy

- Define explicit rollback criteria before deploying. Know what metrics or user reports would trigger a rollback.
- Keep rollback procedures documented and tested. A rollback that has never been practiced will fail under pressure.
- Prefer rollback over hotfix when possible. Hotfixes under pressure often introduce additional bugs.

## Canary and progressive delivery

- Use canary deployments to expose new changes to a small percentage of traffic before full rollout.
- Monitor error rates, latency, and resource usage during the canary phase.
- Promote to full rollout only when metrics are stable and within acceptable thresholds.

## Post-deployment verification

- Verify that the new version is running and healthy. Check process status, health endpoints, and log output.
- Confirm that key user journeys work end to end in the production environment.
- Monitor for a reasonable observation window before declaring the deployment successful.


# Monitoring and observability

Monitoring tells you when something is wrong. Observability tells you why. Invest in both to reduce mean time to detection and mean time to resolution.

## Three pillars of observability

- Metrics: numeric measurements over time. Use metrics for trends, thresholds, and alerting. Examples: request latency, error rate, memory usage.
- Logs: structured or unstructured text records of events. Use logs for debugging, audit trails, and detailed context around incidents.
- Traces: distributed request paths across services. Use traces to understand latency breakdowns and dependencies in microservice architectures.

## Alerting design

- Alert on symptoms, not causes. "Error rate is above threshold" is better than "instance count is low" because the symptom directly impacts users.
- Page only for actionable alerts. If an alert requires no human intervention, it should not wake someone up.
- Set appropriate alert thresholds. Too sensitive creates alert fatigue; too loose misses real incidents.
- Include runbook links in alerts. The person responding should know what to check without hunting for documentation.

## Instrumentation guidelines

- Add metrics at boundaries: API entry points, database queries, external API calls, and queue operations.
- Log with context. Include request IDs, user identifiers, and correlation IDs so you can trace a single request across multiple services.
- Sample traces when volume is high. Full trace collection is expensive; sampling preserves visibility while controlling cost.

## Incident response

- Acknowledge alerts promptly. Even if the issue is not yet understood, confirm that someone is investigating.
- Establish a timeline. Record when the issue started, when it was detected, and what actions were taken.
- Communicate status. Keep stakeholders informed with clear, factual updates at regular intervals.
- Conduct blameless postmortems. Focus on system and process improvements, not individual fault.

- Implement retry logic with exponential backoff for transient failures
- Set reasonable timeouts for all external operations
- Log errors with sufficient context for debugging
- Provide user-friendly error messages for end users
- Clean up resources in finally blocks or defer statements
- Monitor error rates and set up alerts for anomalies

## Refactoring guidelines

- Refactor when you understand the code, not when you're confused by it
- Make small, incremental changes with tests running continuously
- Preserve behavior during refactoring; add tests first if missing
- Extract methods when they have clear, single responsibilities
- Replace magic numbers with named constants
- Remove dead code and commented-out code
- Simplify complex conditionals with early returns or guard clauses
- Keep public APIs stable during internal refactoring
- Use descriptive names that reveal intent
- Review refactored code to ensure readability improved

## Architecture and design principles

- Follow the single responsibility principle
- Design for testability and maintainability
- Prefer composition over inheritance
- Use interfaces and abstractions to decouple components
- Keep dependencies minimal and explicit
- Design for failure with circuit breakers and timeouts
- Separate concerns into distinct layers or modules
- Use dependency injection for flexibility
- Avoid global state and shared mutable data
- Document architectural decisions and trade-offs

## API design and contracts

- Design APIs around use cases, not implementation details
- Use consistent naming conventions and parameter ordering
- Version APIs from the start with clear deprecation policies
- Provide clear error messages with actionable information
- Document all public interfaces with examples
- Use request/response schemas for validation
- Implement rate limiting and authentication at the API layer
- Return consistent response structures
- Support pagination for large result sets
- Provide SDKs or client libraries for common languages

## Data modeling and persistence

- Choose the right data model for access patterns
- Normalize for consistency, denormalize for performance
- Use migrations for schema changes, never direct manipulation
- Index frequently queried fields
- Avoid storing derived data that can be computed
- Use appropriate data types and constraints
- Plan for data growth and archiving strategies
- Implement soft deletes where audit trails are needed
- Use transactions for multi-step data modifications
- Backup critical data with tested restore procedures

## Concurrency and parallelism

- Identify truly independent work for parallelization
- Use thread pools or worker queues for I/O-bound tasks
- Avoid shared mutable state between concurrent operations
- Use locks, semaphores, or atomic operations for synchronization
- Implement timeouts for all concurrent operations
- Handle cancellation and cleanup in concurrent workflows
- Test concurrent code with race condition detectors
- Limit concurrency to avoid resource exhaustion
- Use message queues for decoupled communication
- Monitor thread pools and queue depths in production

## Logging and observability

- Log at appropriate levels: debug, info, warn, error
- Include context in log messages: user ID, request ID, session ID
- Use structured logging with JSON or key-value pairs
- Avoid logging sensitive data: passwords, tokens, personal info
- Log entry and exit points for important operations
- Include timing information for performance analysis
- Use correlation IDs to trace requests across services
- Rotate logs to prevent disk exhaustion
- Centralize logs for analysis and alerting
- Review logs regularly for anomalies and patterns

- Keep secrets out of configuration files
- Version control configuration templates

- Test dependency updates in isolation before merging
- Document why each dependency is needed
- Consider bundle size and runtime overhead
