Create and maintain a structured task list for the current coding session. Tracks progress, organizes multi-step work, and surfaces status to the user.

## When to use
Use proactively when:
- The task requires 3+ distinct steps or actions (not just 3 tool calls for a single conceptual step)
- The work is non-trivial and benefits from planning
- The user provides multiple tasks (numbered or comma-separated) or explicitly asks for a todo list
- New instructions arrive - capture them as todos
- You start a task - mark it `in_progress` (only one at a time) before working
- You finish a task - mark it `completed` and add any follow-ups discovered during the work
- You identify blockers or dependencies between tasks
- Work spans multiple files or systems

## When NOT to use
Skip when:
- The work is a single, straightforward task (or <3 trivial steps)
- The request is purely informational or conversational
- Tracking adds no organizational value

## States
- `pending` - not started
- `in_progress` - actively working (exactly ONE at a time)
- `completed` - finished successfully
- `cancelled` - no longer needed

## Priority levels
- `high` - critical path work, bugs blocking progress, user-critical features
- `medium` - standard work items, normal features
- `low` - nice-to-haves, polish, optimization

## Complexity rating
Rate every task to calibrate effort and approach. Higher complexity means more planning, more verification, and often parallel subagents.

### S1-S4: Simple (seconds to ~5 min)
Quick, low-risk changes. Single file, obvious fix, no architectural decisions.
- **S1**: Trivial — typo fix, single-line change, color tweak, spacing adjustment
- **S2**: Simple — small edit, add a log, update a string, minor config change
- **S3**: Straightforward — multi-line edit in one file, simple function, add a test
- **S4**: Easy multi-step — a few related edits, simple feature, add a helper with tests

### M1-M4: Medium (~5-30 min)
Requires thought, touches multiple files, may need research or decisions.
- **M1**: Moderate — new small feature, add an endpoint, wire up a component
- **M2**: Involved — multi-file feature, refactor a module, add tests + implementation
- **M3**: Challenging — cross-cutting change, new pattern, database migration + code
- **M4**: Complex — significant feature, multiple systems, needs planning + verification

### H1-H4: Hard (~30 min - 2 hours)
Architectural decisions, many files, high risk of breakage, needs careful planning.
- **H1**: Hard — major feature, new subsystem, API redesign
- **H2**: Very hard — cross-system refactor, complex migration, performance overhaul
- **H3**: Difficult — architecture change, new infrastructure, security implementation
- **H4**: Extremely hard — rewrite a core system, complex distributed feature

### U1-U10: Ultra (hours to days)
Massive undertakings that should be broken into many sub-tasks, often parallelized across subagents.
- **U1**: Large project — new app module, full feature area
- **U2**: Major project — multiple subsystems, week-long effort
- **U3**: Huge project — platform-level work, team-scale
- **U4**: Massive — new product, complete rewrite of a system
- **U5**: Ambitious — operating system components, database engine
- **U6**: Extreme — full OS, compiler, game engine
- **U7**: Legendary — distributed systems, large-scale infrastructure
- **U8**: Mythic — enterprise platform, complex ecosystem
- **U9**: Unprecedented — research-grade, novel architecture
- **U10**: Singularity — AI system, full autonomous platform

## Dependencies
Use the `dependencies` field to list task content descriptions that must be completed before this task can start. This creates a natural execution order and helps identify which tasks can run in parallel.

## Time estimates
Use `estimated_minutes` to track how long you expect each task to take. This helps with planning and keeps estimates realistic. Use rough estimates: 5, 10, 15, 30, 60 minutes.

## Tags
Use `tags` to categorize tasks by area or type. Common tags: `frontend`, `backend`, `testing`, `bug`, `feature`, `refactor`, `docs`, `config`, `deps`, `security`.

## Rules
- Update status in real time; don't batch completions
- After creating a list, call this tool before starting the first item.
- After completing each item, call this tool before starting the next item, with the completed item marked `completed` and the next item marked `in_progress`.
- Do not complete multiple items or continue through multiple steps without updating the list between them.
- Mark `completed` only after the required work is actually done, including any required verification. Never based on intent.
- Keep exactly one `in_progress` while work remains
- If blocked or partial, keep it `in_progress` and add a follow-up todo describing the blocker
- Preserve user-provided commands verbatim (flags, args, order)
- Items should be specific and actionable; break large work into smaller steps
- Use dependencies to prevent starting tasks that rely on incomplete work
- Assign priority based on what unblocks other work or is most critical to the user's goal
- Rate complexity honestly — it determines how much planning and verification you should do
- For H3+ and U tasks, consider using `task` subagents to parallelize work
- Break U-rated tasks into many smaller M/S sub-tasks before starting

## Examples

Use it:
- "Add a dark mode toggle and run the tests" -> multi-step feature + explicit verification
- "Rename getCwd -> getCurrentWorkingDirectory across the repo" -> grep reveals 15 occurrences in 8 files
- "Implement registration, catalog, cart, checkout" -> multiple complex features
- "Set up the project and install dependencies" -> deps task with install estimate

Skip it:
- "How do I print Hello World in Python?" -> informational
- "Add a comment to calculateTotal" -> single edit
- "Run npm install and tell me what happened" -> one command

When in doubt, use it.
